## Objective
Define deterministic task assignment, acknowledgement, lease and recovery semantics without expanding agent authority.

## Dispatch order
1. Validate task state, scope and authority.
2. Resolve only registered eligible agents/providers.
3. Apply deterministic capability matching.
4. Select by stable ordering; no model-generated preference.
5. Persist assignment through the M19 control plane.
6. Await acknowledgement within the lease window.

No eligible executor = BLOCKED or HUMAN_ACTION_REQUIRED according to existing governance rules.

## Assignment invariants
- One active assignment per task.
- Assignment cannot exceed task scope or registry authority.
- Provider cannot assign itself.
- Provider cannot change authority.
- Assignment is idempotent.
- Re-dispatch preserves task lineage.

## Acknowledgement
Executor must explicitly ACK the assigned task.

Valid ACK requires:
- matching task_id;
- matching assignment;
- registered executor identity;
- current lease;
- valid source commit/scope.

Wrong executor, stale lease or stale assignment = reject.

## Lease
Lease is execution protection, not authority.

Required fields:
- lease_id
- task_id
- attempt_id
- executor_id
- issued_at
- expires_at
- heartbeat_at
- status

Lease expiry does not delete history. Recovery creates a new controlled attempt/lease.

## Recovery
Expired/unacknowledged lease:
ASSIGNED -> RECOVER_TASK -> new attempt or BLOCKED.

Active acknowledged execution:
EXECUTING + expired lease -> recovery evaluation; never silent duplicate execution.

## Duplicate execution protection
A task may not have two active execution leases simultaneously.

Any conflict is fail-closed.

## Determinism
Selection order:
eligibility -> scope -> capability -> registry status -> stable agent_id.

No LLM ranking.

## Security
- No free AI-to-AI communication.
- No provider self-approval.
- No scope expansion.
- No direct ledger mutation.
- Human Gate remains human-only.
- Conflict round >3 remains BLOCKED.
