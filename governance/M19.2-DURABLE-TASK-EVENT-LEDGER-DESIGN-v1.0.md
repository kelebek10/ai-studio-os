## 1. Decision

M19.2 will add a dedicated durable control-plane persistence boundary.

It will **not** reuse the M18 agent-registry tables as task storage and will not mutate the existing governance/Core schema.

Proposed schema namespace:

`m19_control`

Production creation remains BLOCKED until the separate M19.2 implementation gate is approved.

## 2. Existing controls reused

M19.2 inherits, rather than reimplements, established controls:

- M09 optimistic concurrency/CAS principles;
- M10 monotonic event sequencing;
- M11 exact/conflicting replay idempotency;
- M12 provenance strengthening;
- M14 human approval authority boundary;
- M18 agent-registry/RLS authority boundary;
- M19.1 task command/event contract.

No previous control is weakened by the new ledger.

## 3. Logical entities

### 3.1 task

Canonical task identity and current materialized state.

Required fields:

- task_id UUID PRIMARY KEY
- correlation_id UUID NOT NULL
- parent_task_id UUID NULL
- task_type TEXT NOT NULL
- agent_id TEXT NOT NULL
- scope TEXT NOT NULL
- source_commit TEXT NOT NULL
- status TEXT/controlled enum NOT NULL
- current_sequence BIGINT NOT NULL
- conflict_round INTEGER NOT NULL DEFAULT 0
- requires_human BOOLEAN NOT NULL DEFAULT FALSE
- created_at TIMESTAMPTZ NOT NULL
- updated_at TIMESTAMPTZ NOT NULL

Current state is a projection; the event ledger remains the historical source of transitions.

### 3.2 task_event

Immutable event ledger.

Required fields:

- event_id UUID PRIMARY KEY
- task_id UUID NOT NULL
- correlation_id UUID NOT NULL
- causation_id UUID NULL
- sequence_no BIGINT NOT NULL
- event_type TEXT NOT NULL
- actor_type TEXT NOT NULL
- actor_id TEXT NOT NULL
- source_commit TEXT NOT NULL
- scope TEXT NOT NULL
- payload JSONB NULL
- payload_digest TEXT NOT NULL
- idempotency_key TEXT NOT NULL
- occurred_at TIMESTAMPTZ NOT NULL

Constraints:

- UNIQUE(task_id, sequence_no)
- UNIQUE(task_id, event_type, idempotency_key)
- no UPDATE
- no DELETE for operational roles

### 3.3 task_attempt

Execution attempt history.

Fields:

- attempt_id UUID PRIMARY KEY
- task_id UUID NOT NULL
- attempt_no INTEGER NOT NULL
- executor_id TEXT NOT NULL
- source_commit TEXT NOT NULL
- started_at TIMESTAMPTZ NOT NULL
- acknowledged_at TIMESTAMPTZ NULL
- finished_at TIMESTAMPTZ NULL
- status TEXT NOT NULL
- result_digest TEXT NULL

Constraint:

UNIQUE(task_id, attempt_no)

A failed attempt remains historical.

### 3.4 task_handoff

Bounded result/review/evidence handoff metadata.

Fields:

- handoff_id UUID PRIMARY KEY
- task_id UUID NOT NULL
- attempt_id UUID NULL
- handoff_type TEXT NOT NULL
- source_actor TEXT NOT NULL
- target_actor TEXT NOT NULL
- artifact_digest TEXT NULL
- evidence_digest TEXT NULL
- created_at TIMESTAMPTZ NOT NULL

### 3.5 task_idempotency

Canonical command replay registry.

Fields:

- idempotency_id UUID PRIMARY KEY
- task_id UUID NULL
- command_type TEXT NOT NULL
- idempotency_key TEXT NOT NULL
- request_digest TEXT NOT NULL
- outcome_digest TEXT NULL
- created_at TIMESTAMPTZ NOT NULL

Constraint:

UNIQUE(command_type, idempotency_key)

Conflicting replay of the same key with a different request digest is rejected.

## 4. State/event integrity

A state-changing operation must execute atomically:

1. authenticate/authorize caller;
2. validate command;
3. lock/claim canonical task version;
4. validate expected predecessor state;
5. validate idempotency identity;
6. assign next sequence number;
7. write immutable event;
8. update task projection;
9. commit.

Failure at any step rolls back the entire state-changing operation.

No caller may write the event and projection independently.

## 5. Concurrency

For one task:

- only one transition may claim a given sequence number;
- stale expected state must fail;
- concurrent valid commands cannot produce duplicate sequence numbers;
- exact replay returns the original outcome;
- conflicting replay is rejected.

This follows the previously established CAS/event-sequencing principles instead of inventing a new concurrency model.

## 6. Idempotency

Exact replay:

same command type + idempotency key + request digest

→ return original task/event outcome.

Conflicting replay:

same command type + idempotency key + different request digest

→ BLOCKED/REJECTED.

A retry after a rolled-back transaction may legitimately create the effect once.

## 7. Provenance

Every event carries:

- actor;
- task;
- correlation;
- causation;
- source commit;
- scope;
- timestamp;
- payload digest.

Every result/evidence handoff is linked to the originating task and, where applicable, execution attempt.

M19.2 does not replace the existing EvidenceRecord. It stores the durable lineage pointing to it.

## 8. Authority model

Database roles MUST remain narrower than governance authority.

Initial intended roles:

- control-plane writer: bounded task/event transition functions only;
- control-plane reader: operational read-only access;
- evidence/audit reader: read-only;
- provider: no task-state authority beyond explicitly assigned execution command;
- human approver: existing Human Gate authority only.

No AI provider receives unrestricted INSERT/UPDATE/DELETE access to the ledger.

Direct table mutation by application callers is prohibited where a controlled transition function is required.

## 9. RLS / tenant boundary

If task records become tenant-scoped, tenant context must be explicit and enforced through PostgreSQL RLS.

M19.2 does not introduce tenant semantics by assumption.

No tenant column will be added merely for future speculation. If the existing application contract requires tenant isolation, it becomes an explicit implementation-gate requirement.

## 10. Immutability

Operational roles cannot:

- UPDATE task_event;
- DELETE task_event;
- TRUNCATE task_event;
- rewrite historical attempts;
- rewrite handoff provenance.

Correction occurs through a new event.

The task current-state projection may be updated only through the controlled transition boundary.

## 11. Index baseline

Only evidence-backed indexes are planned:

- task(correlation_id)
- task(status)
- task(agent_id, status)
- task(parent_task_id)
- task_event(task_id, sequence_no)
- task_event(correlation_id, occurred_at)
- task_event(idempotency_key)
- task_attempt(task_id, attempt_no)
- task_handoff(task_id, created_at)
- task_idempotency(command_type, idempotency_key)

No speculative indexing.

## 12. Retention

No automatic deletion policy is introduced in M19.2.

Task/event history is operational evidence and retention policy must be explicitly defined before any cleanup job exists.

## 13. Security tests

The non-production implementation must test:

- unauthorized direct table mutation;
- unauthorized event deletion;
- duplicate sequence race;
- stale transition;
- exact replay;
- conflicting replay;
- rollback + retry;
- provider approval injection;
- forged actor identity;
- wrong task scope;
- wrong agent;
- missing causation;
- digest mismatch;
- event sequence tamper;
- restart recovery.
