# PAI-FORGE — CONSTITUTIONAL AMENDMENT

Document ID: PAI-FORGE-001A
Version: 1.0
Status: CONSTITUTIONAL CONTROL RULE
Applies To: All AI models, agents, workflows, automation and human-supervised project execution
Parent: PAI-FORGE-001 Architecture Constitution
Branch: phase-1-3-foundation

---

# 1. CONTROL-FIRST PRINCIPLE

**Kontrolsüz güç, güç değildir.**

PAI-FORGE shall operate under the following mandatory sequence:

**KONTROL → DOĞRULAMA → KARAR → UYGULAMA → TEKRAR KONTROL**

No AI, agent, workflow or automation may treat unverified progress as completed progress.

No implementation may be promoted solely because it appears reasonable, compiles, passes a superficial check, or is supported by AI consensus.

---

# 2. UNIVERSAL AI / AGENT BINDING RULE

Every AI model and every agent participating in PAI-FORGE shall be bound by this amendment as a prerequisite to work.

Before starting a task, the responsible AI/agent must establish that it has access to and is operating under:

1. the current PAI-FORGE Constitution,
2. this Control-First amendment,
3. the current project state,
4. the applicable task contract,
5. the applicable security and permission rules.

If any required control context is missing, stale, contradictory or unverifiable, the task shall **STOP**.

The AI/agent may report the missing condition, but may not silently continue around it.

---

# 3. NO-BACKWARD-DEBT PRINCIPLE

PAI-FORGE shall not knowingly create technical, architectural, governance, security, data, documentation or operational debt that requires avoidable backward work later.

The following are prohibited:

- knowingly bypassing a required control to gain speed;
- implementing a temporary structure that is expected to be replaced solely because the foundation was not completed;
- creating undocumented interfaces or hidden coupling;
- accepting an unverified dependency as if it were established;
- declaring completion where acceptance evidence is incomplete;
- knowingly creating a state that conflicts with an already-approved architectural or governance rule.

**Forward progress is preferred only when it is controlled progress.**

---

# 4. CONTROLLED GAP / EMPTY BRANCH RULE

When the correct implementation cannot yet be proven, PAI-FORGE may intentionally leave a **controlled empty branch / capability gap**.

A controlled gap is preferable to an incorrect implementation that creates future debt.

A controlled gap must have:

- explicit status;
- reason;
- blocking condition;
- owner or responsible role;
- required evidence for closure;
- no misleading placeholder behavior;
- no false PASS state.

A gap is not considered failure. An uncontrolled workaround is.

---

# 5. STOP CONDITIONS

Any AI or agent shall STOP rather than proceed when one or more of the following exists:

- insufficient evidence;
- contradictory authoritative information;
- missing required input;
- stale project state;
- unclear authority;
- permission mismatch;
- security uncertainty;
- unverified dependency;
- failed acceptance criterion;
- nondeterministic behavior where determinism is required;
- provenance loss;
- possible policy conflict;
- possible architectural regression;
- inability to prove that the proposed change will not create avoidable debt.

The correct result in such cases is **BLOCKED**, **UNVERIFIED**, **UNKNOWN**, or **REQUIRES VALIDATION** as applicable.

---

# 6. DOUBLE-CONTROL RULE FOR MATERIAL CHANGES

Before a material governance, security, architecture, Core-boundary or agent-authority change is written into the repository, the change shall be checked for:

1. consistency with the Constitution;
2. consistency with current project state;
3. security and authority implications;
4. dependency and migration implications;
5. evidence and acceptance criteria;
6. future technical-debt risk.

If the check is incomplete, the change shall not be written as an approved state.

---

# 7. AI CONSENSUS IS NOT CONTROL

Agreement between ChatGPT, Claude, Gemini, Kimi, Copilot or any other AI does not constitute verification.

AI consensus may support analysis, but cannot convert an unverified result into PASS, APPROVED or CORE.

Evidence and deterministic controls remain authoritative.

---

# 8. NO REGRESSION RULE

A new change shall not knowingly weaken an existing verified control, authority boundary, provenance guarantee, reproducibility guarantee, security boundary or governance rule.

If a new requirement conflicts with an existing control, the conflict must be explicitly resolved before implementation.

No silent downgrade is permitted.

---

# 10. CONSTITUTIONAL PRECEDENCE

Where this amendment conflicts with a lower-level task instruction, agent instruction, prompt, workflow shortcut or implementation convenience, this amendment prevails unless an authorized constitutional revision explicitly changes it.

No AI or agent may modify or disable this amendment through ordinary task execution.

Any revision requires the normal constitutional change-control process and explicit human authority where required.

---

# 11. ACCEPTANCE STANDARD

This amendment shall be considered operational only when:

- referenced by the active AI/agent operating model;
- referenced by agent/task contracts;
- included in pre-task control checks;
- included in material-change review criteria;
- reflected in handoff/evidence requirements;
- and verified against the active repository governance state.

Until those integrations are verified, the amendment itself is a constitutional requirement but the integration state shall be recorded as **PENDING INTEGRATION**, not falsely marked complete.
