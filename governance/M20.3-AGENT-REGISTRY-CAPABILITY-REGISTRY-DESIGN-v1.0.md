# M20.3 — Agent Registry + Capability Registry Design v1.0

## Status
M20.3 planning baseline.
M20.2 L0-L4 are closed/passed for non-production implementation acceptance. L5 is not to be falsely marked PASS because no real mobile client exists in the repository.
M20.3 introduces the controlled foundation for placing provider AIs and specialist agents under the Orchestrator.

## Architectural Decision
Agent identity, capability, and task-time authorization are separate concerns.
- Agent Registry answers: Who is this agent?
- Capability Registry answers: What is this agent allowed/capable of doing?
- Task Assignment answers: What may this agent do for this specific task now?
Registry presence alone never grants unrestricted runtime authority.

## Controlled Delegation Flow
ORCHESTRATOR → TASK → CAPABILITY MATCH → AGENT REGISTRY → CAPABILITY AUTHORIZATION → TASK ASSIGNMENT → LEASE → EXECUTION → EVIDENCE → REVIEW → ORCHESTRATOR

Existing M19 control-plane primitives remain authoritative: task, task_assignment, task_attempt, task_handoff, task_lease, task_event, task_idempotency.
M20.3 must extend these primitives rather than replace or redesign them.

## Authority Boundaries
No Provider or Specialist Agent may create arbitrary tasks for itself, self-assign work, directly assign another agent, bypass the Orchestrator, write directly to production, approve governance decisions, self-approve, bypass Human Gate, initiate unrestricted AI-to-AI conversation, or transfer/delegate its capability to another agent.
Specialist-to-specialist delegation is not direct.
Required pattern: SPECIALIST → delegation request → ORCHESTRATOR → capability match → new controlled task.
No agent has approval authority merely because it has execution authority.

## Initial Capability Direction
Example capability for specialist:qwen:security-evidence-analyst: security_evidence_analysis.
Allowed: read_task, inspect_evidence, produce_analysis, submit_evidence.
Prohibited: production_write, governance_approve, task_self_assign, agent_assign, human_gate_bypass.
Provider capabilities must be explicitly registered; no wildcard capability is permitted.

Ensure dispatch can create an assignment only when registry and capability authorization are valid.
### M20.3.5 — Evidence + Review
Agent output remains RESULT_SUBMITTED until controlled review/evidence validation.
### M20.3.6 — Negative Authorization Tests
Required: unauthorized dispatch BLOCK; wrong capability BLOCK; disabled agent BLOCK; environment mismatch BLOCK; direct specialist-to-specialist delegation BLOCK; self-approval BLOCK; Human Gate bypass BLOCK; assignment without capability BLOCK; duplicate idempotency key safe replay; registry/capability provenance mismatch BLOCK or explicit review.

## Security and Governance Rules
- No production mutation in M20.3 foundation work.
- No new provider gets production authority by registration.
- No agent receives governance approval authority.
- Existing maximum conflict rule remains 3 rounds.
- Unresolved conflicts remain BLOCKED / Human Gate.
- Registry and capability definitions must be versioned and traceable to source commit.
- Provider metadata must never become an implicit authority source.
- enabled=true is necessary but not sufficient for task execution; task-time authorization remains mandatory.

## Decision
M20.3 will build the registry/delegation foundation before activating unrestricted multi-agent behavior.
Logical target: Orchestrator → Claude/Gemini/Copilot/Qwen → controlled specialists. This is a target structure, not a declaration that all listed agents are currently runtime-enabled.
